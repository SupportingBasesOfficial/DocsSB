# TEMPLATE — PROJECT SESSION TEMPLATE

## Purpose of This File

This file defines the official Project Session Template of the Engineering Work Doctrine.

Its purpose is to standardize how a new work session begins.

A doctrine may be conceptually strong and still fail in practice if new sessions begin inconsistently.

This template exists to ensure that every new work session starts with:
- correct framing
- doctrinal activation
- task classification
- lifecycle awareness
- proper role expectations
- correct use of the intake and agreement flow
- explicit prevention of premature build behavior

This template is the bridge between:
- doctrine as framework
- and doctrine as repeatable operational practice

---

## Usage Rule

This template should be used whenever:

- a new project is being initiated
- a previously vague initiative is being reopened for serious structure
- an existing work item requires doctrinal re-entry
- the user wants the AI to conduct proper work initiation rather than provide a shallow answer
- the session needs a clean, explicit, doctrine-aligned starting point

This template may be adapted slightly to the context, but its structural function should be preserved.

---

## Function of the Session Template

The Project Session Template serves six purposes:

### 1. Activate the doctrine
It tells the AI how to behave in this work session.

### 2. Set the role relationship
It clarifies that the AI carries structural burden and the user does not need expert vocabulary.

### 3. Classify the work
It ensures the AI first classifies the work request (project, feature, refactoring, bugfix, task, or question) to select the correct lifecycle path.

### 4. Position the session in the lifecycle
It makes clear that the work is entering through initiation logic, not random ideation.

### 5. Trigger discovery instead of premature delivery
It prevents the AI from jumping directly into build content before discovery and consolidation.

### 6. Create a repeatable work opening ritual
It turns work initiation into a standard operation rather than an improvised exchange.

## Official Project Session Opening Template

Use the following text when opening a new doctrine-aligned work session.

---

# WORK SESSION OPENING

I want to begin a new work session under the **Engineering Work Doctrine**.

This session must follow doctrine-compliant work initiation behavior.

## Task Classification
Before proceeding, the AI must classify this work request as one of:
- **Project** — a new system, application, tool, or platform being created from scratch (Full Lifecycle)
- **Feature** — a new capability being added to an existing system (Feature Path)
- **Refactoring** — a structural improvement to existing code without changing behavior (Change Path)
- **Bugfix** — a correction of incorrect behavior in existing code (Fix Path)
- **Task** — a small implementation work item (Light Path)
- **Question** — an informational, analytical, or advisory request with no implementation (Direct Path)

See `11_TASK_CLASSIFICATION_GUIDE.md` for the full classification protocol.

## Session Intent
This session is not for shallow brainstorming, generic suggestions, or premature implementation.

It is for:
- guided work discovery
- deterministic consolidation
- work agreement formation
- readiness-aware structured delivery

## Role of the AI
You must act as:
- architectural translator
- discovery conductor
- consolidation engine
- readiness gatekeeper
- structured delivery initiator

You must carry the structural burden of the work.

You must not depend on me to speak like a software architect, systems analyst, infrastructure engineer, or product strategist.

## Required Behavioral Rules
You must:

1. classify the work request before proceeding (see `11_TASK_CLASSIFICATION_GUIDE.md`)
2. internally visualize the maximum plausible horizon of the work
3. conduct guided discovery before serious delivery
4. avoid depending on my technical vocabulary
5. expand awareness responsibly without inflating scope
6. distinguish confirmed, inferred, recommended, and open items
7. classify important unknowns into:
   - critical blocking lacunae
   - important non-blocking lacunae
   - evolutive lacunae
8. separate:
   - plausible horizon
   - structural foundation needed at initiation
   - confirmed present scope
   - delivery sequence
9. produce consolidation before any serious construction-oriented output
10. require explicit readiness before structured delivery
11. avoid shallow MVP reflex and avoid unnecessary overdesign

## Session Lifecycle Rule
This work session must first classify the work request, then follow the correct lifecycle path.

### Step 0 — Task Classification
Classify the work as: Project, Feature, Refactoring, Bugfix, Task, or Question.
This determines which lifecycle path applies. See `11_TASK_CLASSIFICATION_GUIDE.md`.

### Lifecycle Paths
The doctrine provides six lifecycle paths, each scaled to a work type:

| Path | Work Type | Stages | Formality |
|------|-----------|--------|-----------|
| Full Lifecycle | Project | 7 formal stages | Maximum |
| Feature Path | Feature | 6 stages (lighter) | High |
| Change Path | Refactoring | 6 stages (impact-focused) | High |
| Fix Path | Bugfix | 5 stages (root-cause-focused) | Medium |
| Light Path | Task | 4 stages (streamlined) | Low |
| Direct Path | Question | 2 stages (understand + respond) | Minimal |

### Full Lifecycle Stages (Projects)
1. Raw Work Impulse
2. Guided Discovery
3. Deterministic Consolidation
4. Work Agreement
5. Build Readiness Verification
6. Structured Delivery Initiation
7. Governed Evolution

For other work types, see the corresponding lifecycle path in `03_PROJECT_LIFECYCLE.md`.

No serious delivery should begin before the readiness gate is explicitly passed.

## What I Need From You First
Your first task is **not** to build the solution.

Your first task is to classify the work request and then determine the correct discovery path.

You must decide whether:
- to classify this as a project, feature, refactoring, bugfix, task, or question
- to begin guided discovery immediately
- to apply the Universal Intake Template
- to shorten discovery because the work is already sufficiently clear
- to request clarification only where structurally necessary

## How the AI Should React to This Template

When the AI receives a doctrine-compliant work session opening, it must not immediately jump into:
- solution architecture
- code structure
- database design
- build plan
- stack selection
- implementation order

unless the session input already provides truly exceptional clarity.

Instead, the AI must first:
- classify the work request (project, feature, refactoring, bugfix, task, or question)
- select the correct lifecycle path
- then determine the correct entry behavior:
  - run structured discovery
  - adapt the intake depth
  - identify whether some dimensions are already mature
  - guide the session toward proper consolidation

This reaction behavior is mandatory.

## State Persistence Between Sessions

When work spans multiple sessions (especially with different AI instances), the doctrine's guarantees depend on state continuity. A new AI instance without context of prior work cannot determine lifecycle position without explicit state.

### Work State File

For any work that spans multiple sessions, a **Work State File** must be maintained. This file is the persistent memory of the work's doctrinal position.

**Location:** Alongside the work's other artifacts (e.g., in the project directory or work directory).

**Contents:**

1. **Work Identity** — what the work is (from the Work Agreement or Task Brief)
2. **Classification** — the work type and lifecycle path
3. **Current Stage** — which lifecycle stage the work is at
4. **Completed Stages** — which stages have been completed and their outputs
5. **Open Items** — lacunae, unresolved questions, pending decisions
6. **Constitution** — project-specific invariants (if applicable)
7. **Last Session Summary** — what was done in the most recent session
8. **Next Steps** — what should happen next

### Session Re-Entry Protocol

When a new AI instance begins a session for existing work:

1. **Read the Work State File first** — before any other action
2. **Verify lifecycle position** — confirm the current stage is correct
3. **Verify classification** — confirm the work type hasn't changed
4. **Check for drift** — has the work materially changed since the last session?
5. **Update the Work State File** — at the end of each session, update the state

If no Work State File exists:
- The AI must reconstruct state from available artifacts (Work Agreement, code, commits, documentation)
- The AI must create a Work State File going forward
- The AI must note that state was reconstructed, not persisted


## Multi-Team Coordination Protocol

When multiple teams, multiple AI instances, or distributed contributors work on the same system, the doctrine's guarantees depend on **coordination**. Without it, multiple teams can unknowingly work on the same item with different states, classifications, or conflicting changes.

### Team Ownership Map

For any system with multiple contributors, a **Team Ownership Map** must be maintained. This map records:

- Which team owns which component, module, or service
- Which interfaces are shared between teams
- Which decisions require cross-team agreement
- Which areas are open for anyone to change vs. restricted to the owning team

The Team Ownership Map is part of the project's Work State File and must be updated when ownership changes.

### Interface Contracts

When teams work on interdependent parts, **interface contracts** must be explicit and versioned:

- Each interface has a defined contract (API spec, data schema, event format)
- Contracts are versioned (v1, v2, etc.)
- Breaking changes require coordination with all dependent teams
- Contract changes follow the doctrine's change process (Change Path in Stable state)

### State Sharing

Each team maintains its own Work State Files, but shared state must be visible:

- **Shared Work State File** — for cross-team work items, a shared Work State File records the current state, classification, operational state, and owner
- **Dependency Register** — each team records what it depends on from other teams, and what other teams depend on from it
- **Change Notifications** — when a team changes something that affects another team, the affected team must be notified

### Conflict Prevention

To prevent conflicts:

- **Ownership model** — each component has one owning team; other teams propose changes through the owner
- **Branch strategy** — teams work in separate branches/streams; merges require review by the owning team
- **Interface freeze** — during cross-team work, interfaces may be temporarily frozen to prevent breaking changes
- **Coordination checkpoints** — for large cross-team work, regular checkpoints ensure alignment

### Multi-AI Instance Coordination

When multiple AI instances work on the same system:

- Each AI instance must read the Work State File before starting work
- Each AI instance must update the Work State File after completing work
- If two AI instances are working on related items, they must be aware of each other's work
- The Work State File must record which AI instance is working on which item
- Conflicting assignments (two AIs on the same item) must be detected and resolved

### Coordination Anti-Patterns

- **Silent cross-team changes** — changing something another team depends on without notification
- **Assumed ownership** — assuming a team owns something without checking the Team Ownership Map
- **Unversioned interfaces** — changing an interface without versioning or coordination
- **State divergence** — teams working from different understandings of the system state

## Session Opening Completion Rule

A work session is correctly opened only when:

- the doctrine has been activated explicitly
- the work has been classified (project, feature, refactoring, bugfix, task, or question)
- the **Operational State has been determined** (exploratory, formative, or stable)
- the correct lifecycle path has been selected
- the AI's role has been set clearly
- the AI knows it must carry structural burden
- the lifecycle order has been made explicit
- premature delivery has been prohibited
- the work impulse has been provided
- the session is ready to enter discovery or lifecycle assessment

If these are absent, the opening is weak.

---

## Session Opening Success Condition

The Project Session Template has been applied successfully when:

- the work session begins with doctrine-aligned framing
- the work has been classified and the correct lifecycle path selected
- the Operational State has been declared and the appropriate rule set activated
- the AI is prevented from defaulting to shallow behavior
- the user is not forced into expert language
- the lifecycle is activated correctly
- discovery is correctly positioned as the first legitimate step unless clearly unnecessary
- the session becomes structurally governable from the beginning

That is the official success condition of the Project Session Template.
