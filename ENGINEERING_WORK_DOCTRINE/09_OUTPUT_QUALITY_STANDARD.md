# OUTPUT QUALITY STANDARD

## Purpose of This File

This file defines the official output quality standard of the Engineering Work Doctrine.

Its purpose is to establish how the quality of AI outputs must be judged across the doctrine.

A strong doctrine cannot rely only on philosophical agreement or process compliance.  
It must also define what a good output actually is.

This file exists to prevent weak outputs from being mistaken for strong ones merely because they are:
- articulate
- detailed
- polished
- long
- technically flavored
- strategically framed
- visually well organized

Under this doctrine, an output is not good because it sounds intelligent.

An output is good only if it supports serious work initiation or serious work progression with structural legitimacy.

---

## Role of Output Quality in the Doctrine

Output quality applies across all operational stages of the doctrine, including:
- discovery
- consolidation
- readiness evaluation
- delivery
- governed evolution

Each stage produces a different type of output, but all outputs must still be judged against quality criteria.

The output quality standard protects the doctrine from:
- rhetorical performance without engineering usefulness
- hidden assumptions under confident language
- shallow genericity disguised as clarity
- inflated complexity disguised as sophistication
- project drift caused by low-precision communication
- work drift caused by low-precision communication
- structurally weak guidance wrapped in elegant formatting

This file defines the difference between:
- outputs that look strong
- and outputs that are strong

---

## Foundational Quality Principle

The value of an output is determined by its structural usefulness, not by its rhetorical appearance.

This is the foundational principle of doctrine-compliant quality.

An output must be judged by whether it:
- makes the work more structurally clear
- reduces ambiguity responsibly
- supports correct movement through the lifecycle
- preserves doctrinal integrity
- enables sound engineering decisions
- protects the work from shallow initiation or inflated distortion
- creates usable implementation direction when appropriate

The doctrine rejects output theater.

---

## Official Quality Question

The official quality question is:

**Does this output make the work more structurally legitimate, more governable, and more build-relevant at its current lifecycle stage?**

If not, the output is weak, regardless of how polished it sounds.

---

## Core Dimensions of Output Quality

Every doctrine-compliant output must be judged across the following dimensions.

### 1. Structural Clarity
Does the output make the work more intelligible in structural terms?

### 2. Stage Appropriateness
Does the output match the current lifecycle stage correctly?

### 3. Truthfulness
Does the output distinguish confirmed, inferred, recommended, and open elements properly?

### 4. Relevance
Does the output address the actual work rather than generic work ideas?

### 5. Proportionality
Does the output provide enough depth without overreaching beyond what is justified?

### 6. Build Usefulness
If the work is in a build-legitimate stage, does the output actually help implementation?

### 7. Explicitness
Does the output make important distinctions visible rather than leaving them implicit?

### 8. Integrity Preservation
Does the output protect the work from doctrinal failure?

These dimensions form the quality backbone of the doctrine.

---

## Quality Dimension 1 — Structural Clarity

A high-quality output must increase structural clarity.

It must help the reader understand:
- what the work is
- what it is not
- what is known
- what matters most
- what follows logically
- what remains unresolved
- what should happen next

An output fails this dimension when it:
- repeats what is already known without restructuring it
- adds words without adding meaning
- mixes levels of abstraction carelessly
- sounds intelligent but leaves the work equally vague
- generates more confusion than order

Structural clarity is one of the strongest markers of quality.

---

## Quality Dimension 2 — Stage Appropriateness

An output must fit the lifecycle stage in which it appears.

Examples:
- a discovery output must clarify, not architect
- a consolidation output must synthesize, not merely restate
- a readiness output must judge, not merely encourage
- a delivery output must guide build, not merely admire possibilities

An output fails this dimension when it belongs to the wrong stage.

Common examples of stage-inappropriate output:
- architecture during unresolved discovery
- delivery artifacts before readiness
- generic encouragement instead of readiness judgment
- solution expansion during basic identity clarification
- overbuilt design during consolidation

Doctrine-compliant quality always respects phase legitimacy.

---

## Quality Dimension 3 — Truthfulness

A high-quality output must preserve truth status.

It must make clear, whenever relevant:
- what is confirmed
- what is inferred
- what is recommended
- what remains open

The doctrine considers it a severe quality failure when:
- inference is disguised as fact
- recommendations are presented as confirmed requirements
- open items are hidden inside strong wording
- uncertainty is softened into false certainty
- the output appears more resolved than the project actually is

Truthfulness is not a cosmetic virtue.  
It is a structural requirement.

---

## Quality Dimension 4 — Relevance

A high-quality output must be specifically relevant to the actual work.

It must reflect:
- the work's identity
- the discovered dimensions
- the consolidated meaning
- the known constraints
- the actual maturity of the work

The output fails this dimension when it becomes:
- generic
- templated without adaptation
- detached from the work's real shape
- full of broadly applicable but low-value statements
- interchangeable with outputs for unrelated work

The doctrine allows reusable method, but not generic result.

---

## Quality Dimension 5 — Proportionality

Quality requires proportionality.

The output must provide:
- enough seriousness
- enough depth
- enough specificity
- enough explicitness

without producing:
- unjustified overdetail
- inflated sophistication
- architecture that exceeds maturity
- unnecessary technical performance
- shallow reduction for the sake of speed

An output fails proportionality when it is either:
- too thin for the work's seriousness
- or too heavy for the work's current legitimacy

The doctrine demands calibrated depth.

---

## Quality Dimension 6 — Build Usefulness

When the work is in a build-legitimate phase, output quality must include implementation usefulness.

This means the output should help with things such as:
- deciding structure
- sequencing implementation
- defining artifacts
- clarifying constraints
- shaping data or module boundaries
- preventing architectural confusion
- identifying what should or should not happen next

An output fails this dimension when it:
- sounds strategic but cannot support actual build work
- gives broad ideas without actionable consequence
- avoids making useful distinctions
- produces no usable handoff into technical work

For delivery-phase outputs, build usefulness is non-negotiable.

---

## Quality Dimension 7 — Explicitness

A high-quality output must make important distinctions visible.

It must be explicit where relevant about:
- identity
- scope
- horizon
- sequence
- unknowns
- reservations
- recommendations
- readiness status
- boundaries
- next steps

An output fails this dimension when it leaves too much hidden.

Doctrine-compliant work is not vague by omission.

---

## Quality Dimension 8 — Integrity Preservation

The highest level of output quality includes preservation of doctrinal integrity.

This means the output must not:
- violate the lifecycle
- collapse truth statuses
- authorize build prematurely
- inflate scope without justification
- shrink structural seriousness
- ignore visible blockers
- create fake coherence
- create momentum through distortion

The best-looking output is still low quality if it damages work legitimacy.

---

## Stage-Specific Quality Expectations

Different stages require different output excellence.

### Discovery Output Quality
A discovery output is high quality when it:
- guides clearly
- reduces ambiguity
- uses accessible framing
- surfaces relevant dimensions
- keeps the user from carrying expert burden
- remains disciplined
- prepares consolidation

It fails when it becomes vague, exhausting, overly technical, or prematurely solution-driven.

---

### Consolidation Output Quality
A consolidation output is high quality when it:
- synthesizes discovery into coherent meaning
- distinguishes confirmed vs inferred vs open
- separates scope from horizon
- classifies lacunae
- makes structural implications visible
- prepares the work for contract formation

It fails when it merely restates inputs or fakes coherence.

---

### Readiness Output Quality
A readiness output is high quality when it:
- explicitly states status
- justifies the status structurally
- identifies strengths already present
- identifies remaining gaps
- names blockers when they exist
- specifies the correct next lifecycle step

It fails when it is vague, overly encouraging, overly strict, or structurally unreasoned.

---

### Delivery Output Quality
A delivery output is high quality when it:
- is contract-aligned
- is readiness-authorized
- is build-relevant
- is explicit
- is structured
- is truth-aware
- gives real technical direction
- preserves proportionality
- leaves no dangerous hidden assumptions

It fails when it becomes performance theater, generic output, or unjustified overreach.

---

## High-Quality Output Behaviors

A doctrine-compliant high-quality output usually exhibits the following behaviors:

- it clarifies rather than decorates
- it structures rather than floods
- it interprets rather than merely repeats
- it distinguishes rather than blends
- it guides rather than dazzles
- it preserves boundaries between stages
- it names what is open instead of burying it
- it supports next action without pretending finality
- it helps the work move correctly, not merely quickly

These are practical markers of quality.

---

## Low-Quality Output Behaviors

A doctrine-incompatible low-quality output often exhibits one or more of the following:

- generic language detached from the actual work
- false confidence over unresolved matters
- excessive abstraction with little implementation consequence
- impressive phrasing but weak structural content
- overexpansion into unnecessary complexity
- underexpansion that ignores real structural needs
- confusion between possibility and requirement
- hidden assumptions
- weak sequencing
- phase confusion
- no explicit next step
- no visible distinction between known and unknown

These are signs of output weakness even when the writing appears polished.

---

## Quality and Brevity

The doctrine does not equate quality with length.

A short output may be high quality if it is:
- precise
- structurally sufficient
- stage-appropriate
- explicit
- decision-useful

A long output may be low quality if it is:
- repetitive
- inflated
- vague beneath the polish
- misaligned with stage or need
- non-build-relevant

Length is not the standard.  
Structural usefulness is.

---

## Quality and Detail

The doctrine also does not equate quality with technical detail.

More detail is not automatically better.

Detail is valuable only when:
- readiness justifies it
- the lifecycle stage allows it
- the work needs it
- the user can use it
- it improves implementation legitimacy

Detail without justified relevance is noise.

---

## Quality and Confidence

The doctrine does not reward false decisiveness.

A cautious but explicit output is better than a confident but structurally dishonest one.

High-quality confidence is:
- earned
- bounded
- transparent
- aligned with truth status

Low-quality confidence is:
- performative
- flattening
- assumption-hiding
- misleading

Confidence is only valuable when it is structurally deserved.

---

## Quality Review Questions

Before considering an output doctrine-compliant, the AI should be able to answer yes to the following questions:

- Does this output fit the current lifecycle stage?
- Does it make the work more structurally clear?
- Does it distinguish confirmed, inferred, recommended, and open where needed?
- Does it speak to this actual work rather than to work in general?
- Is the depth proportional to what is justified now?
- If build-relevant, does it help real implementation?
- Does it make important boundaries visible?
- Does it preserve doctrinal integrity?
- Does it clarify what should happen next?

If the answer is no to several of these, the output is not strong enough.

---

## Quality Failure Modes

Output quality has failed when:

- the output sounds intelligent but changes nothing structurally
- the output is clear in language but weak in consequence
- the output is long but not useful
- the output is highly detailed but premature
- the output is concise but too thin to support the work
- the output hides what remains unresolved
- the output generalizes where specificity already exists
- the output gives momentum without legitimacy
- the output damages the doctrine's lifecycle discipline
- the output cannot support the next correct step

These are official output quality failures.

---

## Output Quality Success Condition

An output meets the doctrine's quality standard when:

- it is structurally useful
- it is lifecycle-appropriate
- it is explicit and truthful
- it is work-specific
- it is proportionate
- it is build-relevant when required
- it makes important distinctions visible
- it preserves doctrinal integrity
- it helps the work move correctly to the next stage
- it meets the 100% criterion for its work type (see below)
- it includes the Rigid Payload when it is implementation output (see below)

That is the official success condition of the output quality standard.

---

## The 100% Criterion — Acceptance Standards by Work Type

100% is the floor, not the ceiling. Below 100%, work is not done. But the definition of 100% varies by work type. This table defines what 100% means for each type of work. See `20_ENFORCEMENT_LAYER.md` for how these criteria are enforced through validators and gates.

| Work Type | 100% Criterion |
|-----------|----------------|
| **Code generation** | Compiles + tests pass + no tech debt + meets spec + no broken dependencies |
| **Refactoring** | Identical behavior (proof of equivalence) + cleaner code + no regression |
| **Bugfix** | Root cause resolved + bug test passes + no new bugs |
| **Architecture** | Inevitable components + minimal interfaces + defined invariants |
| **Conceptual answer** | Exact + no irrelevance + no critical omission + semantically precise |
| **Deploy** | Build + tests + health check + rollback + zero downtime + observability |
| **Migration** | Schema validated + sandbox tested + safe rollback + zero data loss |
| **Infra as code** | Template validated + drift + security + cost + idempotent |
| **API design** | Formal contract + versioning + auth + rate limiting + error codes |
| **Security audit** | SAST + DAST + dependency + secrets + zero vulns + attack surface |
| **Performance** | Benchmark + target + regression + profiling + no bottlenecks |
| **Documentation** | 100% APIs + executable examples + diagrams + zero ambiguity |

### How to Apply the 100% Criterion

1. **Before execution:** Identify which criterion applies to the current work type.
2. **During execution:** Execute toward that criterion, not toward "good enough."
3. **After execution:** Verify against the criterion. If any element is missing, the work is not 100%.
4. **When enforcement is present:** Validators check the criterion mechanically. Code that doesn't pass is blocked.
5. **When enforcement is absent:** The AI must self-verify against the criterion. Declaring work complete at 99% is a doctrinal failure.

### The 99% Trap

99% is not "close enough." The 1% gap is a doctrinal failure. It means:
- something compiles but a test doesn't pass
- tests pass but tech debt was introduced
- the fix works but doesn't address root cause
- the answer is mostly right but has a critical omission

None of these are acceptable. The work is either 100% or it is not done.

### Emergency Exception — None

There is no emergency exception to the 100% criterion. Even in production-down scenarios, the fix must address root cause, must not introduce new bugs, and must be verified. Accelerated process is allowed (fast progression through stages, not omission of stages). But 100% remains the floor.

An emergency fix that addresses the symptom but not the root cause will cause the bug to resurface — potentially in a worse form. The 100% criterion exists precisely to prevent this. In emergencies, the cost of a shallow fix is higher, not lower.

If the situation is so urgent that 100% cannot be achieved, the correct response is a temporary mitigation explicitly labeled as such, with a formal follow-up fix scheduled. The mitigation is not the fix. The fix still requires 100%.

---

### Refactoring Without Tests — Special Protocol

The 100% criterion for refactoring requires "identical behavior (proof of equivalence)." But what if the codebase has no tests? How can equivalence be proven?

**When the codebase has no tests, the refactoring 100% criterion is:**

1. **Characterization tests must be written first.** Before any refactoring, the AI must write characterization tests that capture the current behavior of the code being refactored. These tests are not "good tests" — they are "current behavior tests." They document what the code does now, even if what it does is wrong.

2. **Characterization tests must pass before refactoring.** This establishes the baseline.

3. **Refactoring must not break characterization tests.** After refactoring, the characterization tests must still pass. This is the proof of equivalence.

4. **If characterization tests cannot be written** (e.g., code is too coupled to test in isolation), the AI must:
   - state that equivalence cannot be proven through tests
   - apply manual verification (code review, diff analysis, behavioral comparison)
   - label the refactoring as "verified by inspection, not by tests"
   - note this as a quality gap in the Rigid Payload's Enforcement section

5. **The 100% criterion is not waived.** The method of proving equivalence changes, but the requirement does not. "No tests" does not mean "no verification."

This protocol ensures that refactoring without tests is still safe — the AI creates the safety net first, then refactors.

## Operational State and the 100% Criterion

The 100% criterion is not waived by Operational State — it is refined. What "100%" means changes based on the preciousness of the output:

- **Exploratory state:** 100% does not apply. The output is throwaway. The goal is understanding, not durable artifacts.
- **Formative state:** 100% means "100% of current understanding." You must fully understand what you built, even if it will change. You must not ship half-understood code, even in development. But you are not required to meet production-grade criteria (full test coverage, migration ordering, etc.).
- **Stable state:** Full 100%. The work is complete, verified, and production-ready. All criteria apply without exception. In Stable state, "100%" includes the 12 mega-tech protocols (files 23-34) — the work is not 100% if it has not been tested (`23_TESTING_STRATEGY_PROTOCOL.md`), ADRs recorded (`24_ARCHITECTURE_DECISION_RECORDS.md`), observed (`25_OBSERVABILITY_PROTOCOL.md`), security-reviewed (`26_SECURITY_REVIEW_PROTOCOL.md`), technical debt tracked (`27_TECHNICAL_DEBT_PROTOCOL.md`), dependencies evaluated (`28_DEPENDENCY_MANAGEMENT_PROTOCOL.md`), documented (`29_DOCUMENTATION_PROTOCOL.md`), incident response ready (`30_INCIDENT_RESPONSE_PROTOCOL.md`), quality gates passed (`31_QUALITY_GATES.md`), API governance checked (`32_API_GOVERNANCE_PROTOCOL.md`), data governance confirmed (`33_DATA_GOVERNANCE_PROTOCOL.md`), and metrics defined (`34_METRICS_FEEDBACK_LOOP.md`). The mega-tech protocols define what "production-ready" concretely means.

This refinement does not weaken 100% as Floor. It prevents the doctrine from demanding production-grade completion from throwaway or formative work — which would kill iteration without improving quality.

See `21_OPERATIONAL_STATES.md` for the full state definitions and rule mappings.

## Rigid Payload Applicability by Operational State

The Rigid Payload requirement scales with Operational State:

- **Exploratory:** Not required. Output is throwaway.
- **Formative:** Required only for changes being committed as semi-permanent. Experimental changes do not need the Rigid Payload.
- **Stable:** Always required for all implementation work. No exceptions.

See `21_OPERATIONAL_STATES.md` for the full state definitions.

## Rigid Payload — Mandatory Output Format for Implementation Work

When the work involves implementation (projects, features, refactoring, bugfixes), the AI's output must follow the Rigid Payload format. This is 4 mandatory sections:

### Section 1 — Diagnóstico (Diagnosis)

What was the problem. What was the root cause. What needed to change and why.

This section must:
- state the problem clearly
- identify the root cause (not the symptom)
- explain why the change is necessary
- reference the work agreement or task brief that authorized the change

### Section 2 — Alterações (Changes)

What was changed. Which files. Which functions. What was added, modified, or removed.

This section must:
- list every file touched
- describe what changed in each file
- distinguish additions from modifications from removals
- note any structural changes (new modules, changed interfaces, moved code)

### Section 3 — Enforcement

How the changes were verified. Which validators passed. What coverage was achieved. What tests were run.

This section must:
- list which validators were run (type-check, lint, test, security-scan, etc.)
- state the results of each validator
- state test coverage if applicable
- state whether mutation testing was performed (for refactoring)
- confirm that the 100% criterion for the work type was met

### Section 4 — Rollback

How to revert the changes if something goes wrong. What the rollback path is. What the risk areas are.

This section must:
- describe the rollback procedure
- identify risk areas (what might break)
- note any data migrations that need reversal
- state whether the change is reversible without data loss

### When the Rigid Payload Applies

| Work Type | Rigid Payload Required |
|-----------|----------------------|
| Project | Yes |
| Feature | Yes |
| Refactoring | Yes |
| Bugfix | Yes |
| Task | Yes (abbreviated — Diagnóstico + Alterações + Enforcement + Rollback can be brief) |
| Question | No |

### When the Rigid Payload Does Not Apply

For non-implementation work (questions, advisory responses, conceptual analysis), the Rigid Payload does not apply. The output is judged by the 100% criterion for conceptual answers: exact + no irrelevance + no critical omission + semantically precise.

## Output Quality Summary Model

A high-quality output under this doctrine should be:

- clear
- stage-correct
- explicit
- truthful
- relevant
- proportionate
- structurally useful
- non-theatrical
- next-step oriented
- 100% complete (per work type criterion)
- payload-compliant (for implementation work)

If one or more of these are materially absent, the output should not be considered strong.
