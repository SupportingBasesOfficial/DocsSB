# ANTI-PATTERNS

## Purpose of This File

This file defines the official anti-pattern catalog of the Engineering Work Doctrine.

Its purpose is to identify recurring failure modes that can degrade the doctrine in practice.

A doctrine does not remain strong merely because its principles are well written.

It remains strong only if its most common distortions are:
- recognized
- named
- prevented
- corrected when they appear

This file exists to protect the doctrine from silent degeneration.

---

## Role of Anti-Patterns in the Doctrine

Anti-patterns are not minor stylistic issues.

They are recognizable ways in which doctrine-compliant work initiation becomes corrupted.

This file helps prevent:
- shallow work initiation
- false structural confidence
- stage confusion
- AI overreach
- user burden misallocation
- generic work handling
- fake rigor
- fake speed
- fake completeness
- build momentum without legitimacy

An anti-pattern is not simply "something imperfect."

An anti-pattern is a repeatable mode of failure that appears useful in the moment but damages work integrity over time.

---

## How to Use This File

Use this file to:

- audit a live work session
- detect doctrine drift
- evaluate whether a session is still compliant
- explain why a work interaction feels wrong
- harden the doctrine through repeated use
- decide what needs correction before continuing

If a session exhibits one or more anti-patterns, the correct action is not to ignore them.

The correct action is to:
- name them
- understand their consequence
- return to the correct doctrinal behavior

# ANTI-PATTERN 1 — SHALLOW MVP REFLEX

## Description
The AI reflexively reduces the work to a weak minimal version before properly understanding what the work actually needs to be.

This often appears as:
- defaulting to "let's start simple" without structural reasoning
- shrinking the work before discovery is complete
- treating ambition as excess
- replacing serious initiation with a toy foundation
- using MVP language as a shield against thinking

## Why It Is Dangerous
It causes the work to be initiated structurally small, even when the correct long-term shape is already visible.

This often creates:
- rework
- early architectural ceilings
- missing governance
- weak data/control foundations
- false simplicity

## Corrective Action
Return to:
- horizon awareness
- structural foundation analysis
- confirmed scope separation

The doctrine allows phased delivery.  
It does not allow structurally blind initiation.

---

# ANTI-PATTERN 2 — GRANDIOSITY INFLATION

## Description
The AI expands the work into an unnecessarily huge or sophisticated form simply because it can imagine more possibilities.

This often appears as:
- treating all plausible future paths as current obligations
- overloading the work with layers it has not earned
- introducing complexity to sound advanced
- confusing structural seriousness with maximal implementation

## Why It Is Dangerous
It creates:
- overdesign
- false heaviness
- user overwhelm
- misaligned scope
- unnecessary delivery burden

## Corrective Action
Return to:
- operational proportionality
- confirmed present scope
- structural foundation vs horizon separation

The doctrine requires maximum structural awareness, not maximum current scope.

---

# ANTI-PATTERN 3 — USER-AS-ARCHITECT BURDEN

## Description
The AI behaves as though the user must provide architect-level framing, terminology, decomposition, or system structure before serious work can begin.

This often appears as:
- asking overly technical questions too early
- requiring the user to name architecture patterns
- demanding system language the user does not have
- forcing the user to define things the AI should help uncover

## Why It Is Dangerous
It breaks one of the central promises of the doctrine:
that the AI carries structural burden.

It causes:
- user confusion
- stalled discovery
- false dependence on vocabulary
- lower-quality work initiation

## Corrective Action
Return to:
- accessible discovery
- guided decision architecture
- semantic interpretation of user intent

# ANTI-PATTERN 4 — DISCOVERY THEATER

## Description
The AI asks many questions, but the questions do not significantly increase structural clarity.

This often appears as:
- long interrogations with little synthesis
- repetitive clarification with no deeper interpretation
- asking for details that do not affect structure
- making discovery feel busy rather than useful

## Why It Is Dangerous
It creates:
- user fatigue
- false sense of rigor
- delayed progress without real gain
- weak material for consolidation

## Corrective Action
Return to:
- high-value clarification only
- structurally relevant questioning
- synthesis-oriented discovery
- doctrinal ask-vs-infer rules

Discovery must reveal structure, not merely consume messages.

## Description
The AI behaves as though the work is ready without explicitly evaluating readiness.

- moving into delivery automatically after consolidation

# ANTI-PATTERN 23 — SILENT PATH CONTINUATION

## Description
The work type materially changes during execution, but the AI continues on the original lifecycle path without re-classifying.

This often appears as:
- a bugfix that turns out to require refactoring, but the AI continues on the Fix Path
- a feature that turns out to be a new project, but the AI continues on the Feature Path
- a task that grows into a feature, but the AI continues on the Light Path
- the AI noticing the work is bigger than expected but not announcing the change

## Why It Is Dangerous
It creates:
- process mismatch with actual work complexity
- insufficient discovery for the real scope
- hidden structural gaps
- delivery that does not match the work's true nature

## Corrective Action
Return to:
- re-classification when the work type changes
- explicit announcement of path switch
- re-entry into the correct lifecycle path
- Rule 0.4 in `08_DECISION_RULES.md`

Silent path continuation is a doctrinal violation.

# ANTI-PATTERN 24 — SYMPTOM-ONLY FIX

## Description
The AI fixes the visible symptom without addressing the root cause, treating the surface manifestation as the actual problem.

This often appears as:
- patching a bug without understanding why the bug was possible
- adding a workaround without investigating the underlying design issue
- treating the reported error as the full problem
- fixing the immediate issue without examining whether it indicates a deeper structural flaw

## Why It Is Dangerous
It creates:
- recurring problems
- accumulating technical debt
- false sense of resolution
- hidden structural weaknesses that resurface later
- eroding code quality over time

## Corrective Action
Return to:
- root cause analysis
- understanding why the symptom was possible
- addressing the underlying cause, not just the manifestation
- verifying that the fix prevents recurrence, not just the current instance

A fix that does not prevent recurrence is not a fix.

# ANTI-PATTERN 25 — CHANGE WITHOUT UNDERSTANDING

## Description
The AI refactors or restructures code without first understanding why the code is the way it is, treating the existing structure as arbitrary rather than intentional.

This often appears as:
- rewriting code because it "looks wrong" without understanding the constraints that shaped it
- refactoring without discovering the historical reasons for the current design
- imposing patterns without understanding the trade-offs that led to the current approach
- treating existing code as an obstacle rather than a decision with context

## Why It Is Dangerous
It creates:
- loss of implicit knowledge encoded in the existing structure
- reintroduction of problems the original code solved
- regression in behavior that was intentionally designed
- alienation of developers who understand the original context
- structural changes that miss the point of the original design

## Corrective Action
Return to:
- brownfield discovery (`15_BROWNFIELD_DISCOVERY_PROTOCOL.md`)
- understanding the forces that shaped the current code
- codebase analysis before change planning
- respecting that existing code represents decisions, not accidents

Change should be informed by understanding, not driven by preference.

# ANTI-PATTERN 26 — WORKAROUND

## Description
The AI solves the symptom instead of the root cause. The direct solution seemed hard, so a workaround was applied.

This often appears as:
- patching around a problem instead of fixing the underlying cause
- applying a band-aid solution because the real fix seemed difficult
- choosing the indirect path because the direct path required more study
- treating "it works" as sufficient when the approach is structurally wrong

## Why It Is Dangerous
It creates:
- recurring problems that resurface in different forms
- accumulating technical debt from layered workarounds
- false sense of resolution
- eroding code quality as workarounds compound
- a codebase where the real logic is hidden beneath accumulated patches

## Corrective Action
Return to:
- root cause analysis (Rule 6.3 in `08_DECISION_RULES.md`)
- studying until the direct path is clear (Rule 6.2 in `08_DECISION_RULES.md`)
- the 80/20 principle — more understanding, not more patching
- rejecting the workaround as a legitimate execution strategy in Stable state

**State refinement:** Workarounds are prohibited in Stable state. In Exploratory/Formative state, workarounds are allowed with notes (see `21_OPERATIONAL_STATES.md`). The anti-pattern applies when workarounds are used in Stable state, or when they are used in Formative state without being noted as intentional debt.

If the direct solution seems hard, understanding is incomplete. Study more, not less.

# ANTI-PATTERN 27 — EXECUTION WITHOUT STUDY

## Description
The AI jumps to EXECUTAR without passing through ENTENDER and ESTUDAR. The 80/20 principle is violated. The first execution is not the correct one.

This often appears as:
- immediately writing code without understanding the problem
- skipping the execution flow stages because the task "seems simple"
- trial-and-error execution instead of informed execution
- producing output before studying the existing system, constraints, and root cause

## Why It Is Dangerous
It creates:
- incorrect first attempts that require rework
- solutions that address the wrong problem
- hidden assumptions baked into code without verification
- wasted effort on approaches that were doomed from the start
- loss of the doctrine's core protection: that the first execution must be the correct one

## Corrective Action
Return to:
- the 5-stage execution flow (ENTENDER → ESTUDAR → PLANEJAR → EXECUTAR → VERIFICAR)
- the 80/20 principle (Rule 6.4 in `08_DECISION_RULES.md`) — 80% effort in understanding, 20% in execution
- passing through ENTENDER and ESTUDAR before any execution
- the requirement that the first execution must be the correct one

Tentativa-e-erro não chega ao rastro. Study first, execute once.

# ANTI-PATTERN 28 — PAYLOAD MISSING

## Description
The AI produces implementation output without the Rigid Payload — no Diagnóstico, Alterações, Enforcement, or Rollback sections. The AI produced code without reasoning, verification, or rollback path.

This often appears as:
- code changes delivered without explaining what the problem was and its root cause
- implementation without stating what was changed and why
- output with no verification or enforcement section showing how correctness was confirmed
- no rollback path provided — no way to revert if the change is wrong
- treating the Rigid Payload as optional decoration rather than mandatory structure

## Why It Is Dangerous
It creates:
- untraceable changes — no diagnosis of what was wrong
- unverifiable changes — no enforcement section to confirm correctness
- irreversible changes — no rollback path if the change introduces new problems
- code without reasoning — the AI produced output without structured thinking
- loss of the enforcement layer's core guarantee: that implementation work is reasoned, verified, and reversible

## Corrective Action
Return to:
- the Rigid Payload format (Rule 6.6 in `08_DECISION_RULES.md`, `20_ENFORCEMENT_LAYER.md`)
- the 4 mandatory sections: Diagnóstico, Alterações, Enforcement, Rollback
- treating the Rigid Payload as mandatory for all implementation work, not optional
- producing the payload before or alongside the code, not as an afterthought

Implementation output without the Rigid Payload is incomplete by definition.

# ANTI-PATTERN 29 — SILENT BYPASS

## Description
The AI bypasses enforcement validators without explicit acknowledgment. Using `--no-verify` without stating why. Hiding that validators were skipped.

This often appears as:
- running `git commit --no-verify` without explaining which validators were skipped and why
- declaring work complete when validators were not run or were bypassed
- hiding the fact that enforcement gates were skipped
- treating validator failures as annoyances to work around rather than signals to address

## Why It Is Dangerous
It creates:
- false confidence that work passed enforcement when it did not
- hidden quality gaps that would have been caught by validators
- erosion of the enforcement layer's integrity — bypasses that are invisible cannot be audited
- a culture where skipping verification is normal rather than exceptional
- work that appears verified but was never actually checked

## Corrective Action
Return to:
- Rule 6.7 in `08_DECISION_RULES.md` — bypasses must be explicit and visible
- stating clearly when and why a validator was bypassed
- treating `--no-verify` as a discouraged last resort, not a convenience
- making every bypass visible, justified, and acknowledged

Silent bypasses are doctrinal violations. If validators must be skipped, the skip must be stated.

# ANTI-PATTERN 30 — 99% ACCEPTED

## Description
The AI declares work complete at 99%. Below 100%, work is not done. The 1% gap is not "close enough" — it is a doctrinal failure.

This often appears as:
- declaring work "done" when one validator still fails
- accepting "almost passing" as sufficient
- treating a single failing test as a minor issue rather than a blocker
- saying "it's basically complete" when 100% has not been achieved
- rationalizing the gap as insignificant

## Why It Is Dangerous
It creates:
- work that is declared complete but is not actually complete
- accumulated small gaps that compound into systemic quality erosion
- normalization of incomplete work as acceptable
- loss of the doctrine's core quality standard: 100% as floor, not ceiling
- a precedent where "close enough" becomes the de facto standard

## Corrective Action
Return to:
- Principle 2 in `02_OPERATIONAL_PRINCIPLES.md` — 100% as Floor
- Rule 6.7 in `08_DECISION_RULES.md` — work that does not pass 100% cannot be declared complete
- resolving the remaining 1% before declaring completion
- treating the gap as a doctrinal failure, not a rounding error

Below 100%, work is not done. The 1% gap is the difference between doctrine-compliant work and doctrinal failure.

# ANTI-PATTERN 31 — TESTING THEATER

## Description
The AI writes tests that appear comprehensive but do not actually verify critical behavior. Tests exist, the suite passes, but the system is not verified.

This often appears as:
- writing only happy-path tests and skipping error, exception, and edge-case paths
- chasing 100% line coverage instead of behavior coverage — tests that execute code without asserting meaningful behavior
- writing tests that are trivially correct and never fail, giving false confidence
- skipping the test types required for the work type (e.g., no integration tests for a Feature, no regression test for a Bugfix)
- treating test count or coverage percentage as the goal instead of behavioral verification

## Why It Is Dangerous
It creates:
- false confidence that the system is verified when critical paths are untested
- defects that pass through a green test suite into production
- a test suite that provides no safety net during refactoring — tests that do not assert the right things cannot catch regressions
- wasted effort maintaining tests that verify nothing
- erosion of the doctrine's "100% as Floor" guarantee — 100% of meaningless tests is still 0% verification

## Corrective Action
Return to:
- the Testing Strategy Protocol (`23_TESTING_STRATEGY_PROTOCOL.md`)
- behavior coverage, not line coverage — every public function, every branching path, every error path must be tested
- the test types required for the work type and operational state (see the Test Requirements by Work Type table)
- the test quality standards: deterministic, independent, fast, meaningful
- the requirement that a Bugfix must include the regression test that would have caught the bug

Tests that do not verify behavior are not tests. A green suite with untested critical paths is testing theater, not verification.

# ANTI-PATTERN 32 — RETROACTIVE ADR

## Description
The AI makes a significant architectural or technical decision without recording an ADR, or writes the ADR after the decision is already implemented as a formality rather than as a decision-making tool.

This often appears as:
- implementing a technology choice or architectural pattern and only writing the ADR afterward to "check the box"
- writing an ADR with no real alternatives considered — the decision was already made, and alternatives are fabricated to justify it
- skipping the ADR entirely because the decision "seemed obvious"
- recording the decision but not the context, so the ADR says what was decided but not why
- making decisions that are hard to reverse without any durable record of the reasoning

## Why It Is Dangerous
It creates:
- decisions that cannot be understood by future maintainers — they see what was decided but never why
- repeated debates over decisions that were already made, because the rationale was never recorded
- undoing of decisions for reasons that were already considered and rejected, because the reasoning was lost
- false sense of governance — an ADR written after the fact is documentation, not decision-making
- loss of the institutional memory that ADRs exist to preserve

## Corrective Action
Return to:
- the Architecture Decision Records protocol (`24_ARCHITECTURE_DECISION_RECORDS.md`)
- writing the ADR before or during the decision, not after implementation
- the mandatory ADR sections: Context, Decision, Alternatives Considered, Consequences
- the rule that an ADR without alternatives considered is not an ADR — it is a statement of preference
- the rule that when in doubt, write one — the cost of an unnecessary ADR is low; the cost of a lost decision is high

An ADR records reasoning, not just outcomes. A retroactive ADR is a postmortem of a decision, not a record of one.

# ANTI-PATTERN 33 — OBSERVABILITY AS AFTERTHOUGHT

## Description
The AI treats observability as optional or as something to be added later, delivering functionality without the logs, metrics, traces, alerts, and dashboards needed to operate the system in production.

This often appears as:
- delivering a feature with no structured logs, no metrics, and no traces
- adding observability only after an incident reveals the system is opaque
- treating observability as a "nice to have" rather than a delivery requirement on equal footing with functionality and tests
- adding bare `console.log` statements instead of structured logs with required fields
- shipping to production with no alerts configured, so the team learns about problems from users instead of from the system

## Why It Is Dangerous
It creates:
- systems that cannot be debugged in production — when something breaks, there is no data to investigate
- incidents that take longer to diagnose and resolve because the system is a black box
- false confidence that the system is healthy because there are no alerts — no alerts means no monitoring, not no problems
- operational dependence on tribal knowledge — the only person who can debug the system is the person who wrote it
- a system that violates the doctrine's requirement that Stable state work includes observability

## Corrective Action
Return to:
- the Observability Protocol (`25_OBSERVABILITY_PROTOCOL.md`)
- the three pillars: structured logs, metrics, and traces — all three are required, not just one
- the observability requirements by work type and operational state
- treating observability as a delivery requirement, not an add-on
- the principle that a system that works but cannot be observed is not ready for production

Observability is not "we'll do it later." A system that cannot be seen cannot be operated. Observability is a delivery requirement.

# ANTI-PATTERN 34 — SECURITY REVIEW AS CHECKBOX

## Description
The AI treats security review as a formality — running automated scans and declaring security review complete without actually examining the security-relevant areas of the work.

This often appears as:
- running a SAST scan, seeing no critical findings, and declaring security review done
- skipping manual review of authentication, authorization, input validation, and data protection because the automated scan passed
- applying the wrong security review level — using Level 1 (Automated) for work that requires Level 2 (Manual) or Level 3 (Expert)
- declaring "no security concerns" without checking the security review scope areas
- treating security review as a step to rush through at the end rather than a genuine evaluation

## Why It Is Dangerous
It creates:
- vulnerabilities that automated scans cannot detect — authorization logic flaws, business logic abuse, insecure data handling
- false confidence that work is security-reviewed when only the cheapest check was run
- production systems with exploitable security gaps that a manual review would have caught
- erosion of the security review protocol's integrity — a rubber-stamp review provides no real protection
- exposure to supply chain, data breach, and compliance risks that the review was supposed to prevent

## Corrective Action
Return to:
- the Security Review Protocol (`26_SECURITY_REVIEW_PROTOCOL.md`)
- the correct security review level for the work — Level 1 (Automated) is not sufficient for changes to auth, data access, or external interfaces
- the full security review scope: authentication, authorization, input validation, output encoding, data protection, secret management, dependency vulnerabilities, error handling, rate limiting, audit trails
- treating security review as a genuine evaluation, not a formality
- the requirement that security review is completed before declaring 100% in Stable state

A security review that checks nothing meaningful is not a security review. Automated scanning is the floor, not the ceiling.

# ANTI-PATTERN 35 — UNTRACKED TECHNICAL DEBT

## Description
The AI incurs technical debt — intentionally or unintentionally — without recording it in the Debt Register, allowing debt to accumulate silently and invisibly.

This often appears as:
- taking a shortcut to meet a deadline without noting it as intentional debt with a payoff plan
- accumulating unintentional debt through poor practice and never acknowledging it
- knowing that a piece of code is debt-laden but not recording it because "we'll fix it later"
- deferring tests, documentation, or observability without creating a debt entry
- treating the Debt Register as optional rather than as the mandatory tracking mechanism it is

## Why It Is Dangerous
It creates:
- invisible debt that compounds until the system becomes unmaintainable
- no payoff plan — debt that is not tracked is debt that is never paid
- false sense of system health — the code looks like it works, but the debt is hidden
- knowledge loss — the context of why debt was incurred is lost when it is not recorded
- a system where the debt burden is unknown, making prioritization impossible

## Corrective Action
Return to:
- the Technical Debt Protocol (`27_TECHNICAL_DEBT_PROTOCOL.md`)
- the Debt Register — every debt item must be recorded with type, severity, owner, and payoff plan
- the distinction between intentional debt (acceptable in Formative with a note) and unintentional debt (always a defect)
- the rule that intentional debt without a note is unintentional debt
- the Consolidation Moment requirement to review and record debt before entering Stable state

Debt that is not tracked is debt that is never paid. Untracked debt is the most dangerous kind — it grows silently until it blocks everything.

# ANTI-PATTERN 36 — CASUAL DEPENDENCY ADDITION

## Description
The AI adds a third-party dependency without evaluating it against the dependency criteria, treating dependency addition as a trivial choice rather than a supply chain and maintenance decision.

This often appears as:
- adding a library because it is convenient without checking license compatibility
- pulling in a dependency without scanning for known vulnerabilities
- adding a package without checking if it is actively maintained
- ignoring transitive dependencies — adding a small package that pulls in hundreds of transitive packages
- not evaluating alternatives — adding the first dependency found without checking if a better or lighter option exists
- using floating ranges (`^`, `~`, `latest`) in Stable state instead of pinning exact versions

## Why It Is Dangerous
It creates:
- supply chain risk — a compromised or vulnerable dependency can exfiltrate secrets, inject malicious code, or open backdoors
- license risk — an incompatible license (e.g., GPL) can impose copyleft requirements on the project
- maintenance burden — unmaintained dependencies stop receiving security fixes and become liabilities
- bloated bundles and slower installs from unnecessary transitive dependencies
- reproducibility risk — floating ranges mean the version installed today may not be the version installed tomorrow

## Corrective Action
Return to:
- the Dependency Management Protocol (`28_DEPENDENCY_MANAGEMENT_PROTOCOL.md`)
- the dependency evaluation criteria: necessity, license, security, maintenance, popularity, compatibility, transitive dependencies, size, performance, documentation, alternatives
- the rule that a dependency that fails a critical criterion must not be added in Stable state
- pinning exact versions and using lockfiles in Stable state
- the principle that if the functionality is trivial to implement, implement it instead of adding a dependency

Every dependency is code written by someone else running inside your trust boundary. Adding a dependency without evaluation is a security decision made blindly.

# ANTI-PATTERN 37 — STALE DOCUMENTATION

## Description
The AI writes documentation once and never updates it, or updates code without updating the documentation that describes it, so the documentation becomes misleading rather than helpful.

This often appears as:
- writing architecture docs for the initial system and never updating them when the architecture changes
- updating API behavior without updating the API documentation
- writing runbooks that describe a deployment process that no longer matches the actual process
- leaving onboarding docs outdated so new contributors follow instructions that do not work
- treating documentation as a one-time deliverable rather than as living documentation that must evolve with the system

## Why It Is Dangerous
It creates:
- documentation that is worse than no documentation — outdated docs actively mislead
- wasted time for new contributors who follow instructions that do not work
- operational errors when runbooks describe procedures that no longer apply
- loss of trust in documentation — when docs are known to be stale, people stop reading them
- institutional knowledge that exists only in tribal memory, because the written record is wrong

## Corrective Action
Return to:
- the Documentation Protocol (`29_DOCUMENTATION_PROTOCOL.md`)
- the documentation requirements by work type — updating relevant docs is part of completing the work
- the principle that documentation is living — it must evolve with the system
- updating architecture docs when structure changes, API docs when interfaces change, runbooks when operational behavior changes
- treating documentation updates as part of the Rigid Payload, not as a separate optional task

Documentation that does not match the system is not documentation — it is a liability. Living documentation means documentation that is updated when the code is updated.

# ANTI-PATTERN 38 — BLAMEFUL POST-MORTEM

## Description
The AI or team conducts a post-mortem as a blame-assignment exercise rather than a root-cause analysis, focusing on who caused the incident instead of why the system allowed it to happen.

This often appears as:
- asking "who made the change that caused the incident" instead of "what systemic gap let the change through"
- assigning individual blame rather than identifying process, tooling, or systemic failures
- skipping the post-mortem entirely because "it was just a mistake" and no systemic lesson is extracted
- writing a post-mortem that lists human error as the root cause without examining why the system did not prevent the error
- using the post-mortem to justify punishment rather than to drive corrective action

## Why It Is Dangerous
It creates:
- a culture of fear where people hide incidents and near-misses instead of reporting them
- recurring incidents — blaming a person does not fix the systemic gap that allowed the incident
- no corrective actions — if the root cause is "human error," there is nothing to fix
- loss of the learning that post-mortems exist to capture
- erosion of psychological safety, which is the foundation of honest incident reporting

## Corrective Action
Return to:
- the Incident Response Protocol (`30_INCIDENT_RESPONSE_PROTOCOL.md`)
- the blameless post-mortem principle — focus on systemic causes, not individual blame
- the post-mortem template: incident summary, timeline, root cause, contributing factors, corrective actions
- the rule that "human error" is never the root cause — the root cause is the systemic gap that allowed the error to cause an incident
- tracking corrective actions to closure — a post-mortem without completed corrective actions is incomplete

A post-mortem that blames a person fixes nothing. A post-mortem that fixes the system prevents the next incident. Blamelessness is not softness — it is rigor.

# ANTI-PATTERN 39 — GATE AS SUGGESTION

## Description
The AI treats a failed quality gate as a warning rather than a blocking checkpoint, proceeding past the gate without an explicit override or fixing the failure.

This often appears as:
- continuing to the next lifecycle stage when a gate fails, treating the failure as advisory
- noting that a gate failed but proceeding anyway without recording an explicit override
- treating gate failures as inconveniences to work around rather than signals to address
- weakening gate criteria to make them pass instead of fixing the underlying issue
- skipping gate verification entirely because "the work is clearly done"

## Why It Is Dangerous
It creates:
- stage drift — the quiet slide from one stage to the next without proven completion
- defects that pass through the pipeline because gates were treated as optional
- false confidence that the pipeline is enforcing quality when it is not
- erosion of the quality gates protocol — a gate that does not block is not a gate, it is a decoration
- untraceable quality failures — when gates are bypassed silently, there is no record of what was skipped

## Corrective Action
Return to:
- the Quality Gates Protocol (`31_QUALITY_GATES.md`)
- the four properties of every gate: criteria, verification, blocking, override
- the rule that a failed gate is a stop, not a warning — work remains in the current stage until the gate passes
- the override mechanism — if a gate must be bypassed, the override is explicit, visible, recorded, and justified
- the principle that a gate without blocking is a decoration, and a gate without override is a wall

A gate that does not block is not a gate. If the gate fails, work stops. If the gate must be bypassed, the bypass is stated, not hidden.

# ANTI-PATTERN 40 — AD-HOC API DESIGN

## Description
The AI designs each API endpoint in isolation without following the governance conventions, producing an API surface that is inconsistent, unpredictable, and hard to maintain.

This often appears as:
- using verbs in URLs for some endpoints (`/getUsers`) and nouns for others (`/users`)
- mixing naming conventions — camelCase in some endpoints, snake_case in others
- making breaking changes without versioning — changing response schemas or error formats that break existing consumers
- designing error handling inconsistently — different error envelope formats across endpoints
- implementing the API first and defining the contract afterward, instead of contract-first
- skipping API documentation because the endpoint "is simple enough"

## Why It Is Dangerous
It creates:
- an API surface that consumers cannot predict — learning one endpoint does not help them use the rest
- breaking changes that silently break consumer integrations
- maintenance burden — inconsistent conventions mean every endpoint is a special case
- integration friction — consumers must read documentation for every endpoint instead of relying on conventions
- an API that cannot be governed because there is no consistent standard to enforce

## Corrective Action
Return to:
- the API Governance Protocol (`32_API_GOVERNANCE_PROTOCOL.md`)
- the API design principles: consistency, predictability, explicitness, versioning, documentation, contract-first
- the naming conventions: resources as nouns, plural for collections, lowercase with hyphens, consistent field naming
- the versioning strategy: breaking changes are versioned, not silent
- the error handling conventions: consistent error envelope across all endpoints
- contract-first design — the contract is defined before implementation

An API without governance is a collection of personal choices. An API with governance is a contract that consumers can rely on. Consistency is not aesthetic — it is functional.

# ANTI-PATTERN 41 — UNCLASSIFIED DATA

## Description
The AI handles data without classifying it by sensitivity first, treating all data the same — applying Public-level protections to Restricted data, or over-protecting Public data with unnecessary controls.

This often appears as:
- storing personally identifiable information (PII) or credentials without encryption because no one classified it as Restricted
- applying the same access controls to all data regardless of sensitivity
- logging sensitive data fields because no one checked the data classification before adding log statements
- skipping audit trails for Confidential and Restricted data because classification was never performed
- treating data classification as "obvious" without explicitly assigning a level and following the handling requirements

## Why It Is Dangerous
It creates:
- data breaches — Restricted data stored without strong encryption is a critical incident waiting to happen
- regulatory violations — PII, PHI, and payment data handled without compliance controls trigger legal consequences
- over-access — without classification, least privilege and need-to-know cannot be enforced because sensitivity is unknown
- audit gaps — access to sensitive data is not logged because no one knew it was sensitive
- a system where data protection is based on guesswork instead of policy

## Corrective Action
Return to:
- the Data Governance Protocol (`33_DATA_GOVERNANCE_PROTOCOL.md`)
- the four classification levels: Public, Internal, Confidential, Restricted
- the handling requirements by classification — encryption, access control, logging, and retention scale with sensitivity
- the data access principles: least privilege, need-to-know, audit trail, access review, no shared credentials
- the rule that classification is the foundation of governance — you cannot protect what you have not classified

Data that is not classified is data that is not governed. Handling Restricted data with Public-level controls is not a simplification — it is a defect.

# ANTI-PATTERN 42 — VANITY METRICS

## Description
The AI collects metrics that look good on a dashboard but do not drive action, or collects metrics without feeding them back into doctrine evolution, so measurement becomes decoration rather than a feedback loop.

This often appears as:
- tracking metrics that are easy to measure but not actionable — "total lines of code," "number of commits," "test count"
- collecting DORA metrics but never acting on them — deployment frequency is tracked but change failure rate is ignored
- building dashboards that no one looks at after the initial creation
- tracking doctrine-specific metrics but never using them to refine the doctrine — classification accuracy is measured but the classification guide is never updated when accuracy is low
- treating metrics collection as the goal rather than the feedback loop it feeds

## Why It Is Dangerous
It creates:
- false sense of measurement — the team believes it is data-driven because metrics exist, but no decisions are informed by them
- wasted effort maintaining metrics and dashboards that no one uses
- blind spots — the metrics that matter (change failure rate, MTTR, post-mortem action closure) are not tracked, so problems are invisible
- a doctrine that cannot evolve — without feedback, the doctrine cannot know if its mechanisms are working
- metric fatigue — when metrics never drive action, people stop collecting them, and the feedback loop breaks entirely

## Corrective Action
Return to:
- the Metrics & Feedback Loop Protocol (`34_METRICS_FEEDBACK_LOOP.md`)
- the DORA metrics: deployment frequency, lead time for changes, change failure rate, MTTR
- the doctrine-specific metrics: classification accuracy, state accuracy, discovery completeness, first execution success, rigid payload compliance, gate pass rate, post-mortem action closure, technical debt payoff rate
- the feedback loop — metrics must drive action: if classification accuracy is below 90%, the classification guide needs refinement; if gate pass rate is below 90%, the gates or the work process need adjustment
- the principle that a metric without a feedback loop is decoration, not measurement

Metrics that do not drive action are vanity. The purpose of measurement is not to feel good about numbers — it is to identify what needs to change and to change it.

## Anti-Pattern Review Questions

When auditing a session, ask:

- Are we asking too much or too little?
- Are we building too early?
- Are we pretending clarity we do not yet have?
- Are we using doctrine language without doctrine behavior?
- Are we shrinking the work blindly?
- Are we inflating the work blindly?
- Are we mixing horizon with scope?
- Are we skipping readiness?
- Are we hiding assumptions?
- Are we still in the correct lifecycle stage?
- Are we applying too much process for this work type?
- Are we applying too little process for this work type?
- Has the work type changed without re-classification?
- Are we fixing symptoms instead of root causes?
- Are we changing code without understanding why it is the way it is?
- Are we applying a workaround instead of fixing the root cause?
- Are we executing without studying first?
- Are we producing implementation output without the Rigid Payload?
- Are we silently bypassing enforcement validators?
- Are we declaring work complete below 100%?
- Are we writing tests that do not verify critical behavior?
- Are we making significant decisions without recording an ADR?
- Are we shipping functionality without observability?
- Are we treating security review as a checkbox?
- Are we incurring technical debt without tracking it?
- Are we adding dependencies without evaluation?
- Are we leaving documentation stale after code changes?
- Are we conducting blameful post-mortems or skipping them?
- Are we treating failed quality gates as warnings?
- Are we designing APIs without following governance conventions?
- Are we handling data without classifying it by sensitivity?
- Are we collecting metrics that do not drive action?

If the answer suggests drift, a correction is needed.
